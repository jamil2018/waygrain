# Freshness and explicit review

Source content/revision/reference changes, application version changes and mapped-target changes mark affected retained claims `needs_review`. Missing/ambiguous mappings and unknown application versions remain visible. Unaffected claims retain their metadata. The authoring service/import boundary adds these warnings; the store rejects unmarked successors and attempts to clear warnings or change verification metadata through ordinary writes. Initial imported records retain their supplied evidence classes; importing code does not create verification.

A stale code claim can retain its **historical** verification actor, method, time, scope and supplied code revision while pointing to the changed source for review. That historical verification does not establish the new revision or scope. The current source excerpt/hash/revision and the old verification remain separately visible; immutable bundle history retains the prior exact source and claim. A claim with a mismatched supplied revision or verification version cannot be current. Other verification scope dimensions must still match; only historical version differences are allowed in a review-required record. This exception is confined to `needs_review` records.

Reading documentation or opening a source never advances verification time. Clarification must use the same freshness metadata. Matching labels/layout/structure cannot verify hidden business rules.

In the editor's Claims and sources section, save or reload all draft changes first. Review the precise supplied source or run the synthetic behavior test, select that method, then choose **Record explicit verification**. The service records its trusted author identity, the selected method, server time, exact current scope and (for a code-verified claim) supplied code revision in a new immutable bundle/claim revision. It does not upgrade evidence class, erase unknowns, reconcile conflicts or delete old evidence. Unknown versions or unresolved mappings refuse verification. Clock rollback before the prior verification/recorded instant is refused.

The author-only `POST /api/verify` request contains `schema_version:1`, `expected_revision`, project/app/claim IDs, exact scope and method (`supplied-source-review` or `synthetic-behavior-test`). Host/Origin and author authorization are required. Client-supplied actor/time fields and structural-similarity methods are rejected. These are explicit synthetic author attestations, not proof of a real-host inspection or universal behavior qualification.
