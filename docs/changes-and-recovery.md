# Changes and recovery

`wg_changes` (CLI `changes`) compares two visible retained captures or a scoped inclusive end revision range `(from_revision, to_revision]`. Only matching screens/scopes, normalizer versions and redaction profiles are comparable. Subtree mismatches are explicit. Incomplete observations cannot establish removal. Results cite evidence IDs and paginate with revision/filter-bound cursors and whole-envelope byte limits.

Control comparison uses structural positions, not an identity inference: reordering or inserting a node can produce altered positions. Noninteractive structural changes also use the control subject. Tabs and modals compare descriptive view state. A changed feature-variant projection returns incomparable coverage because the v1 change vocabulary cannot express it precisely; it never implies an application action outcome. Revision comparisons include new annotations/supersessions and recorded action outcomes. A range containing an incompatible observation returns incomparable rather than claiming complete coverage. Range work stops at 500 captures and 500 graph records; cutoffs and invalidated-reference limits set `complete: false`. Historical edges retain their original endpoints.

`wg_plan_refresh` (CLI `refresh-plan`) is declarative and read-only. New compatible complete captures advance a state/screen check time; partial fragments have their own observed time and do not reset that check, even when they exceed the evidence summary limit. Replay, query and planning do not refresh. Original transition traces and the weakest flow observations retain their check times. A refreshed screen cannot reverify them. Plans expand flows to deduplicated transition steps, require an authorized before/action/after trace, preserve expected historical view/scope, and flag matching passed assertions for test-verified facts. Changed historical endpoints require checks even within the age limit. Unknown/hidden targets and step cutoffs remain unresolved; no plan executes scripts or grants action authority.

Maintenance commands select only the startup configuration. `backup --config /absolute/private/config.json` and `export --config ...` allocate private `backup-UUID.sqlite` and `export-UUID.json` files in its fixed storage directory. Save the backup receipt’s UUID and SHA-256. `restore --config ... --backup UUID --sha256 HASH` requires every server/store connection to close; peers return `STORE_BUSY`. It checks private regular files, checksum, standalone image (no sidecars), exact supported schema/constraints, project/app identities, integrity and foreign keys before staging a replacement. Restore preserves IDs, revisions and evidence; it invalidates older cursors with a durable local epoch. Backup uses SQLite’s online backup API, normalizes to a standalone image, and returns the revision inside that image. Never copy a live WAL database as a backup.

JSON export is versioned archival data containing retained IDs, scopes, redacted evidence, provenance, graph histories, receipts and tombstones; there is no JSON import. Deleted history remains until explicit permanent purge. Both exports and backups include historical records, not merely visible query results. They are not encrypted. Exclude the storage directory and artifacts from version control through your own ignore rules.

Restore retains a private `pre-restore-UUID.sqlite` image with any matching WAL/SHM sidecars, including when the previous store is corrupt. This is a forensic retention set, not a certified backup. A valid old WAL is checkpointed before replacement, then a verified stage file replaces the database atomically and the directory is synced. If a crash interrupts before replacement, the valid old image remains; after replacement the verified backup remains. Temporary output IDs are never filesystem paths in MCP requests. No CLI maintenance operation edits host settings.

`delete-scope`, `undo-delete`, `purge-preview` and `purge` take strict JSON on stdin with schema/project/app IDs. Deletion adds `scope`, `request_id` and `expected_store_revision`; undo replaces `scope` with `deletion_batch`. Recoverable tombstones hide all currently visible records in exactly that scope and preserve every ID/link for undo. Retries are idempotent. Ingestion and commits cannot revive deleted identities; undo or an explicitly previewed purge is required. Replaying a purged/deleted graph or capture request refuses rather than returning hidden evidence.

Purge is separate: run `purge-preview` with scope, inspect total/per-kind counts and bounded sample IDs, then pass its `preview_token` and same scope to `purge`. A changed revision/restore epoch invalidates the preview. Purge requires exclusive lifetime maintenance access, refuses retained graph dependencies rather than broadening its scope, and erases only selected tombstoned records. `storage_reclaimed` reports whether post-commit vacuum/checkpoint completed. Independent backup/export/pre-restore files still retain their data. Safe request digests/receipts and browser attempt markers remain to prevent replaying application side effects; purge is not an erasure claim about backups, journal safety markers or physical media.

The default cap is 100 MiB of database plus WAL, reported by status. Ingestion reserves a conservative upper bound for changed SQLite pages/WAL before commit; it can refuse before the exact cap rather than exceed it. `STORAGE_LIMIT` leaves committed history and revisions unchanged. Increasing the configured cap, archiving/backing up then explicitly deleting/purging, or moving to a new configured store are operator remediation choices. Lowering the cap never prunes existing history, and reads, idempotent existing replay, deletion and undo remain available above the cap. Export/backup files and coordination are separate from this intake cap.

`tests/recovery-process.test.mjs` exercises separate-process contention, bounded busy refusal, actual SIGKILL of uncommitted writes, killed real v3→v4 migration SQL before commit, failed migration rollback, retained pre-migration image, future-schema byte preservation, live lifetime-lock refusal, and restore kills immediately before/after the real database rename. Test-only native/builtin barriers make kill boundaries deterministic without production hooks. Assertions compare committed captures/revisions/foreign keys and entire query envelopes. These are process-crash tests on a local filesystem; they do not attest hardware power-loss recovery or other operating systems.
