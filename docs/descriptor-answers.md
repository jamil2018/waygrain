# Bounded clarification contract

Clarification preparation authorizes exact project/app/environment/version/role/tenant/state before retrieving any provider-facing source. Component packages include applicable page facts; page packages include permitted components. Target/page identity is checked explicitly. The detached evidence package uses the existing 32 KiB/32-claim bound and preserves missing/truncated markers, conflicts and freshness. Provider input is recursively frozen plain data: no store, DOM, tool or application-action capability is supplied.

The local fixture contract uses finite, evidence-derived answer templates. It recognizes the exact acceptance question “Why is the total 90 for 10 items at 10 each?”, its direct nine-item variant, “What about 9?” with a trusted same-conversation calculation basis, discount-rule questions and tax gaps. Unsupported questions become a generic canonical request before reaching a provider. Raw unsupported question text is not echoed. Follow-up basis includes every identity and scope dimension and cannot transfer to another conversation/target/context. This bounded grammar is deliberate; it is not general-purpose AI or tax interpretation.

A supported calculation requires the exact synthetic rule from an applicable documented source, or the pinned supplied Calculate code hash with matching recorded verification. Inferred or label-only evidence cannot establish the formula. Documented evidence is preferred deterministically, then pinned code verification. Altered/missing evidence produces a specific gap rather than an invented formula. Conflicts return the available conflicting claims and citations without reconciliation. A stale rule stays visibly review-required; questions do not update verification. The formula is fixture-specific, not a claim about real application behavior.

Answers carry scope, target/page/conversation IDs, descriptor revision, provider label, text, precise claim/source revision/hash/locator citations, evidence classes, unresolved conflicts, missing information and warnings. Validation independently reconstructs the allowed answer from the authorized package and requires an exact schema/content match. Valid citation IDs cannot legitimize unsupported prose, fabricated arithmetic, class upgrades, omitted conflicts or an injected tool field. Answer text is bounded to 8 KiB, citations to 32, conflict metadata to 64 IDs and the complete answer to 32 KiB. Larger conflict unions retain an unresolved answer with explicit conflict-metadata and incomplete-evidence omission markers; omissions never establish a reconciliation. Invalid results produce `INVALID_ANSWER`; exceptions/timeouts produce sanitized `PROVIDER_UNAVAILABLE`, never raw provider messages. Execution defaults to a two-second timeout, configurable only in trusted code up to five seconds.

`AnswerProvider` is vendor-neutral, but future adapters must satisfy this bounded output contract and be explicitly configured and separately qualified. The interface does not supply actions; it is not a runtime sandbox for arbitrary provider implementation code. No external model/provider is invoked by preparation or validation. The offline `deterministicProvider()` adapter uses this same contract. Its frozen 13-case matrix covers supported and unsupported questions, same-scope follow-up, tax gaps, conflicting sources, stale evidence, unknown version, isolated tenant/version and missing mappings. Tests prohibit outbound fetches and confirm unchanged stored evidence. Persisted conversations and UI follow in W17/W18. Default development requires no keys or paid network calls. Public release remains HOLD.
