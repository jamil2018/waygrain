# Evidence graph and recall

D01 adds `wg_commit` through core, stdio MCP and `waygrain commit --config /absolute/config.json` (JSON request on stdin). It accepts annotations, supersession, explicit identity aliases, actions, action events and observed transitions. Flows and test-run operations complete the commit surface.

Commits require the current store revision. A batch is atomic; successful writes advance once. Request keys share the existing receipt namespace. Identical sanitized replay returns its original receipt even after a later write; changed payloads conflict. Request-local references normally resolve earlier operations. Test-run links and assertion targets may refer forward within the same atomic batch; missing references reject the batch.

Annotation values and inferred rationales, and alias rationales, must exactly match a whitespace-normalized phrase in an operator-reviewed `allowed_labels` profile. Add reviewed safe descriptions to configuration explicitly; arbitrary free text fails before hashing or persistence. Evidence remains untrusted data. IDs, runner and trace aliases must be nonidentifying operator metadata. No retained text executes or authorizes browser actions.

Observed annotations require direct capture support for their target. Inferred annotations retain their rationale and never become observations. Partial captures can support annotations on that capture only, making the coverage boundary explicit. Contradictory annotations coexist; supersession retains the previous record and must match its target and kind. Structured `wg_evidence` returns annotations, their provenance and cited IDs; summary freshness is unknown rather than a verification claim.

Aliases are audited same-kind, same-app, same-scope links with capture evidence covering both endpoints. Both histories remain intact; self-links, cycles and a second alias for one source fail. Ingestion and stored flows do not silently retarget aliases.

Store schema v2 preserves v1 IDs, revisions, evidence and receipts. Migration requires exclusive coordination authority, takes a private consistent backup of an existing v1 store, rebuilds the record-kind constraint transactionally and checks integrity/foreign keys before commit. The historical v1 schema is unchanged. Migration tests use an actual v1 database; later recovery gates remain separate.

D02 validates a before/action/after trace atomically. An action belongs to its source state and optional source control. Events require identical app, scope, session, tab and trace, strictly increasing sequence numbers, ordered timestamps, and complete capture endpoints. Capture and event sequences share a collision check in both write paths. Successful events require an after capture; failed/cancelled/timeout attempts can retain a null after ID but cannot establish a transition. Transitions must match the exact event, endpoint captures, states, action and outcome. Guards are reviewed safe phrases, never executed. Application effects and graph writes remain separate; an accepted report is a caller attestation.

D03 flows retain the exact ordered transitions and declared scope. Each transition must start where the previous one ended; scopes cannot mix. Test runs retain runner/version, application version, times, outcome and scoped assertions. Assertion evidence must cover the target and fall within the declared run interval. A transition/flow assertion needs the actual action event or both endpoint captures for every transition; a snapshot alone cannot test-verify an action. Only a matching passed assertion in a passed run can confer `test_verified`. Failed/skipped runs remain evidence. A passing run does not upgrade other records. Atomic test-verification can reference a later run through local refs; assertion target refs can link new records in that same batch, with final validation before commit. Other refs resolve earlier records. Application versions and assertion text also require reviewed safe phrases.

D04 exposes `wg_query` search and neighbors via core, MCP and `waygrain query --config /absolute/config.json`. Search ranks exact ID first, then exact name/tag, then normalized lexical substrings, with stable ID tie breaks. Search filters apply within one exact configured scope. Semantic name/tag annotations remain separately attributed records and never rewrite structural names or provenance. Active supersession hides the prior annotation from name/tag matching, while history remains retrievable.

Neighbors follow typed relations, capture evidence joins and validated action/trace links. They default to one hop and cap at three, with a 500-record visit limit. The whole serialized envelope obeys record/byte budgets; output is complete, no matches or explicitly incomplete. Continuations bind filters and revision; any write makes old cursors stale. Queries never launch a browser, write records or refresh evidence. Summaries expose provenance, coverage, observation age, known application version and conflicts, without asserting backend behavior.

Schema v3 adds tombstone visibility storage; query and evidence retrieval exclude active tombstones. Scoped deletion, undo and purge commands are still Phase E. Existing v2 stores migrate under exclusive coordination with private consistent backup; new stores and v1 upgrades retain their history. Status counts describe all retained records, including hidden history. Later freshness/change/maintenance gates remain separate.

D05 adds bounded breadth-first path traversal over observed or test-verified transitions, and ordered flow retrieval. Inferred edges and transitions with hidden evidence/dependencies cannot form a usable path. Direction and exact historical IDs are preserved. Transition guards and action preconditions are returned for host evaluation; guarded paths are conditional. Failed outcomes, stale evidence or a newer complete state can require inspection, without retargeting controls. Conditional results retain these evidence limits and warnings too.

Depth defaults/caps at eight and visits at 500; edge examination is additionally capped at 500. Flow depth is its ordered transition count. Traversal cutoff is explicitly incomplete, distinguishable from completed no-path search. Record/byte pagination is separate, using the same revision/filter-bound cursor rule; reaching a traversal cutoff never silently becomes a complete answer. No query executes or refreshes anything.
